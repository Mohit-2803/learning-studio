UNDER THE HOOD

What happens when you run a query?

1
Your app sends a request

The query and any variables are sent to the GraphQL endpoint.

2
The schema checks it

The server checks field names, types, and required inputs against its API contract.

3
Resolvers find the data

A resolver is the server function that supplies a field’s value, perhaps from a database or another service.

4
You get a shaped response

The server returns JSON containing the fields you selected, or helpful errors if the request is invalid.

SAY IT IN YOUR OWN WORDS
Four interview scenarios
Answer aloud before opening the notes. Focus on explaining your reasoning and the trade-offs.
When is GraphQL useful, and what does the backend need to provide?
Explain the graph-shaped schema, client-selected fields, typed validation, resolver layer, and the actual data source. GraphQL is an API layer, not a database or a frontend-only feature.
A nested query is slow. How do you investigate and improve it?
Inspect resolver traces and database timings, identify repeated N+1 lookups, batch related keys with request-scoped loaders, add indexes where appropriate, and measure again.
A response contains both data and errors. What should the client do?
Inspect errors and their paths alongside data. Explain how nullable fields affect propagation, show partial successful fields when safe, and distinguish validation failures from resolver failures.
How would you design a private, paginated live feed?
Cover stable cursor ordering and page limits, identity from trusted server context, per-record authorization, query-cost/rate controls, and whether subscriptions justify their transport and reconnect complexity.
